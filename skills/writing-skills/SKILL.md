# Создание навыков

## Приоритет правил пользователя

В проектах Валерия применяются СУИИР и прямые указания пользователя. Они важнее процесса ниже. Сохраняй пользовательские данные и существующую работу; не удаляй их без необходимого разрешения. Проверки и способ установки выполняй с учётом действующих инструкций среды и задачи.

## Обзор

**Создание навыков — это разработка через тестирование, применённая к документации процессов.**

**Личные навыки хранятся в каталоге навыков рабочей среды**: в Claude Code это `~/.claude/skills/`. Пути для других сред см. в [codex-tools.md](../using-superpowers/references/codex-tools.md) и [gemini-tools.md](../using-superpowers/references/gemini-tools.md). Codex, Copilot CLI и Gemini CLI также распознают `~/.agents/skills/` как общий путь.

Сначала создаются тестовые сценарии — ситуации давления для субагентов, затем наблюдается исходное нарушение без навыка, пишется сам навык, проверяется соблюдение инструкций и устраняются лазейки.

**Главный принцип:** если ты не видел, как агент ошибается без навыка, ты не знаешь, обучает ли навык именно нужному.

**НЕОБХОДИМАЯ ОСНОВА:** до применения этого навыка разберись с `superpowers:test-driven-development`. Он определяет цикл RED–GREEN–REFACTOR, который здесь адаптирован к документации.

**Официальные рекомендации:** дополнительные рекомендации Anthropic находятся в [references/anthropic-best-practices.md](references/anthropic-best-practices.md). Они дополняют подход этого навыка.

## Что такое навык?

**Навык** — справочное руководство по проверенным техникам, шаблонам или инструментам. Он помогает будущим агентам находить и применять работающие подходы.

**Навыки — это:** повторно используемые техники, шаблоны, инструменты и справочники.

**Навыки — не:** рассказ о том, как однажды была решена проблема.

## Соответствие TDD и создания навыка

| Понятие TDD | Создание навыка |
|---|---|
| **Тестовый случай** | Сценарий давления с субагентом |
| **Production-код** | Документ навыка SKILL.md |
| **Тест падает — RED** | Агент нарушает правило без навыка: исходное поведение |
| **Тест проходит — GREEN** | Агент соблюдает правило с навыком |
| **Рефакторинг** | Закрытие лазеек при сохранении соблюдения |
| **Сначала тест** | Исходный сценарий выполняется ДО написания навыка |
| **Увидеть падение** | Дословно записать оправдания агента |
| **Минимум кода** | Написать навык против конкретных нарушений |
| **Увидеть прохождение** | Проверить, что агент теперь соблюдает правило |
| **Цикл рефакторинга** | Найти новые оправдания → закрыть лазейки → перепроверить |

Весь процесс следует циклу RED–GREEN–REFACTOR.

## Когда создавать навык

**Создавай, когда:**
- Техника не была для тебя интуитивно очевидной.
- Ты будешь обращаться к ней в разных проектах.
- Подход применим широко, а не только к одному проекту.
- Он будет полезен другим.

**Не создавай для:**
- Одноразовых решений.
- Стандартных практик, уже хорошо описанных в других местах.
- Соглашений конкретного проекта: помещай их в файл инструкций проекта.
- Механических ограничений: если проверку можно обеспечить регулярным выражением или валидатором, автоматизируй её; документацию оставь для решений, требующих суждения.

## Типы навыков

### Техника
Конкретный метод с последовательностью действий: condition-based-waiting, root-cause-tracing.

### Модель
Способ думать о проблемах: flatten-with-flags, test-invariants.

### Справочник
Документация API, синтаксис и инструменты, например работа с офисными документами.

## Структура каталога

```text
skills/
  skill-name/
    SKILL.md              # Основная инструкция, обязательна
    supporting-file.*     # Только при необходимости
```

**Плоское пространство имён:** все навыки доступны для поиска в одном пространстве.

**Выноси в отдельные файлы:**
1. Объёмный справочник от 100 строк: документацию API или подробный синтаксис.
2. Повторно используемые инструменты: скрипты, утилиты, шаблоны.

**Оставляй внутри SKILL.md:** принципы, понятия, примеры кода до 50 строк и остальное содержание.

## Написание SKILL.md

Поле `description` описывает только условия применения: поводы и признаки, начинаясь с «Используй, когда…». Не пересказывай в нём процесс работы: прочитав краткий процесс, агент может следовать ему вместо чтения навыка.

При создании или изменении заголовка YAML, имени, описания либо сокращении файла читай [references/discovery.md](references/discovery.md): шаблон SKILL.md, описание и ключевые слова, наименование, расход токенов и ссылки между навыками.

## Примеры кода

**Один отличный пример лучше множества посредственных.**

Выбирай подходящий язык:
- Техники тестирования → TypeScript/JavaScript.
- Системная отладка → Shell/Python.
- Обработка данных → Python.

**Хороший пример:** полный, запускаемый, с комментариями о том, ПОЧЕМУ сделано именно так, из реального сценария; ясно показывает приём и готов к адаптации.

**Не следует:** реализовывать пример на пяти и более языках, делать шаблоны с пропусками или выдуманные искусственные случаи. Одного качественного примера достаточно: его можно перенести на другой язык.

## Организация файлов

### Самодостаточный навык
```text
defense-in-depth/
  SKILL.md    # Всё содержимое внутри
```
Применяется, если весь материал помещается и объёмный справочник не нужен.

### Навык с повторно используемым инструментом
```text
condition-based-waiting/
  SKILL.md    # Обзор и приёмы
  example.ts  # Работающие вспомогательные функции
```
Применяется, если инструмент содержит повторно используемый код, а не просто описание.

### Навык с объёмным справочником
```text
pptx/
  SKILL.md       # Обзор и процессы
  pptxgenjs.md   # Справочник API на 600 строк
  ooxml.md       # Справочник структуры XML на 500 строк
  scripts/       # Исполняемые инструменты
```
Применяется, если справочный материал слишком велик для основного файла.

В тексте вызывай включённые скрипты через интерпретатор: `bash scripts/tool.sh`, `node scripts/tool.js`, а не напрямую по пути. Некоторые упаковщики удаляют права на исполнение; прямой вызов `scripts/tool.sh` в таком случае завершается ошибкой `Permission denied`.

## Непреложное правило — как в TDD

```text
НИКАКОГО НАВЫКА БЕЗ ПРЕДВАРИТЕЛЬНОГО ПАДАЮЩЕГО ТЕСТА
```

Исходная методика относит это к НОВЫМ навыкам и ИЗМЕНЕНИЯМ существующих. В ней предлагается удалить навык или изменение, написанные до теста, и начать заново, не оставляя их как образец и не адаптируя при тестировании. Исключения для небольших дополнений, новых разделов и обновления документации не предусмотрены. Смысл удаления — именно удаление. **При этом соблюдай приоритет выше: пользовательские файлы и результаты не удаляются без необходимого разрешения.**

**НЕОБХОДИМАЯ ОСНОВА:** `superpowers:test-driven-development` объясняет причины; те же принципы применяются к документации.
