# SDD: направление проверки в пределах отдельной задачи

Сделать проверки каждой задачи в subagent-driven-development дешевле и быстрее без ослабления качества: ограничить запросы проверяющим рамками задачи и прекратить дублирование работы, сохранив широкий охват итоговой проверки ветки.

## Проблема

Проверяющие качества кода в SDD регулярно проводят для diff одной задачи работу масштаба проверки всей ветки. Доказательства получены из двух реальных локальных сеансов SDD: `a1a6719a-6109-453a-9933-34ae396f5bae` — sen-core-v2 и `0cc1a12d-9984-4c35-8615-9d42dadb2c47` — serf, оба в `~/.claude/projects/`:

- В сеансе sen-core-v2 семь из восьми проверяющих качества выполняли поиск по всему репозиторию; наиболее дорогой запустил более 50 команд Bash примерно за 200 секунд. В двух сеансах проверки качества обходились в 4–8 раз дороже проверок спецификации для тех же задач.
- Проверяющие спецификации, получавшие указание «читайте только файлы из этого diff, не исследуйте весь код», оставались в заданных рамках: 6–16 вызовов инструментов, 14–65 секунд.
- Ни один проверяющий самостоятельно не запускал тяжёлые тесты. Каждый замеченный повторный запуск тестов или запуск всего пакета прямо запрашивался контроллером в формулировках вроде «проверь все использования», «запусти тесты, если полезно, особенно на гонки», «читает ли ещё что-то `Meta()`?».

Первопричины по степени влияния:

1. **Запрос проверки качества задачи наследует формат проверки готовности к слиянию.** `code-quality-reviewer-prompt.md` делегирует работу `requesting-code-review/code-reviewer.md`, где рассматриваются архитектура, масштабируемость, безопасность, готовность к эксплуатации и задаётся вопрос «готово к слиянию?». Такой контекст поощряет исследование всей ветки ради одной задачи. Ограничение чтения diff из запроса проверки спецификации сюда не перенесли.
2. **У контроллера нет инструкций по составлению запросов проверяющим.** Он придумывает открытые указания вроде «проверь все использования», которые проверяющие воспринимают буквально.
3. **Работа дублируется на разных этапах.** Критерий «соответствие плану» шаблона качества повторяет только что проведённую проверку спецификации. Проверяющие заново запускают наборы тестов, которые исполнитель уже выполнил на том же коде и отразил в отчёте вместе с результатами TDD.
4. **Для задачи и итоговой проверки используется один шаблон.** Различие «узкая проверка задачи, широкая проверка ветки» нигде не выражено.

Проблему впервые указал полевой отчёт `~/2026-06-09-code-quality-reviewer-scope-budget-issue.md`. Указанный в нём сеанс и основные числа проверить не удалось, но качественный диагноз подтвердился в двух реальных локальных сеансах. Исправление к отчёту: сквозные проверки — например, порядка блокировок или изменённых контрактов — иногда являются *правильным* методом ревью. Расширение охвата нужно разрешать при сформулированном конкретном риске, а не запрещать.

## Цели

- Проверять каждую задачу в её границах: сначала diff, расширение при обосновании, без повторного запуска одних и тех же тестов.
- Сохранить широкий охват итоговой проверки всей ветки.
- Не ухудшить обнаружение ошибок.

## Что не входит в цели и что сохраняется

- **Полные повторные проверки сохраняются.** После исправления проверяющий снова рассматривает всю задачу с полной глубиной чтения, но не повторяет тесты, которые исполнитель только что запустил на изменённом коде. Так сознательно отклоняется предложенный полевым отчётом «бюджет повторной проверки»: стоимость его худшего примера, повторного ревью с `-race` и циклами `-count=100`, ограничивается правилами запуска тестов ниже, а не сокращением чтения.
- ~~**Два этапа проверки остаются раздельными:** соответствие спецификации и качество кода проверяют независимые субагенты последовательно.~~ **Заменено последующими итерациями стоимости:** реальные оценки показали преобладание накладных расходов каждого запуска, и сопровождающий разрешил рассмотреть все варианты. Теперь задачу проверяет один проверяющий с двумя выводами; независимая широкая итоговая проверка остаётся.
- **Координатор сохраняет право выбора модели.** Никакой уровень модели проверяющего не навязывается.
- **`requesting-code-review/` не меняется.** Он остаётся широким шаблоном итоговой проверки ветки и произвольных ревью.
- Порядок выводов сохраняется: сначала соответствие спецификации, затем качество; циклы исправлений и повторных проверок и требование устранять Critical/Important остаются.

## Итерации стоимости после запуска оценок

Реальные запуски до и после показали увеличение стоимости после усиления инструкций о доказательствах, передаче ограничений и чистом выводе: go-fractals вырос с 42,8 минуты и 14,5 млн токенов в первой версии с ограничением задачи до 69,9 минуты и 32,2 млн в усиленной версии, достигнув качества на уровне исходной версии — слепая оценка 8,5 против 8,5. Профилирование ходов субагентов выявило причины по убыванию влияния: дешёвые модели делали в 2–3 раза больше ходов в многоэтапной работе, 678 из 1197 ходов субагентов приходились на haiku; накладные расходы запусков — три субагента на задачу, каждый заново определяет diff, координация контроллера стоила половину расходов; подробные повествования для соблюдения правила доказательств.

- **Итерация 1:** указания учитывать число ходов, а не только цену токена — минимальный средний уровень для многоэтапной работы; необязательная вставка diff в запрос; краткие ссылки на доказательства вместо пересказа; определение Important как проблемы, из-за которой результату нельзя доверять до исправления; запуск исправлений только для Critical/Important. Результат: 68,2 минуты и 22,9 млн токенов — на 29% меньше токенов, длительность почти не изменилась. При необязательной формулировке контроллеры вставили diff только в 2 из 22 запросов проверяющим.
- **Итерация 2:** проверки спецификации и качества задачи объединены в `task-reviewer-prompt.md`: один проверяющий, одно чтение diff, два вывода; один исполнитель исправлений обрабатывает оба вида замечаний. Исполнитель запускает целевой тест во время работы и полный набор один раз до коммита. Результат go-fractals: 47,5 минуты, 15,7 млн токенов, 13,55 доллара — лучше исходного состояния по всем показателям; слепая оценка 9/10 против 7/10.
- **Итерация 3:** критерии явно относят блокирующие слияние проблемы сопровождаемости — дословное дублирование, подавление ошибок, тесты без проверок — к Important; замечания Minor должны передаваться в итоговое ревью для разбора. Скептический подход распространяется на обоснования проектных решений исполнителя: «оставлено по YAGNI» — утверждение, а не окончательный вывод. После того как совет вставлять diff в запрос применяли только в 0–6 из 11–17 запусков по понятным причинам экономии контекста, diff стали передавать файлом: `git diff > /tmp/sdd-task-N.diff`; перенаправление не помещает его в контекст контроллера, а проверяющий читает одним вызовом Read.
- **Итоговая зафиксированная конфигурация e355795:** все пять сценариев проходят. Go-fractals — 44,4 минуты, 13,4 млн токенов, 11,67 доллара, относительно исходного состояния −32% времени, −37% токенов и −27% долларов. Svelte-todo — 62,8 минуты, 19,7 млн, 15,76 доллара: −21%, −28%, −25%. `rejects-extra-features` — 1,31 против 1,88 доллара; `spec-reviewer-flaws` без изменений. Сценарий внесённого дефекта v3 проходит: решение, требующее суждения, должно прозрачно отмечаться, а тест, название которого обещает проверку, но фактически ничего не проверяет, подлежит обязательному исправлению. Дефект обнаружен и устранён.

## Проект

### Общий принцип: не повторять тесты на неизменившемся коде

Отчёт исполнителя содержит результаты тестов и доказательства TDD RED/GREEN именно для проверяемого кода. Проверяющие подтверждают их чтением. Проверяющий запускает тест только тогда, когда чтение вызвало конкретное сомнение, на которое существующий запуск не отвечает; в этом случае запускается целевой тест, а не весь набор. В средах, где субагенты-проверяющие имеют только чтение, например Antigravity сопоставляет их шаблоны с типом `research` без доступа к командам, проверяющий указывает в отчёте, какой тест он запустил бы.

После исправления исполнитель повторно запускает тесты, покрывающие изменённый код; повторный проверяющий не дублирует этот запуск. Сейчас это условие ничем не обеспечено: `implementer-prompt.md` описывает только первоначальный цикл реализации, тестов и коммита, без инструкций для исправлений. Поэтому спецификация добавляет в него правило: после исправления замечания повторно запустить покрывающие изменённый код тесты и включить результаты в отчёт об исправлении.

Принцип присутствует в обоих запросах проверяющим, запросе исполнителю и инструкциях контроллеру.

### 1. Самостоятельный `skills/subagent-driven-development/code-quality-reviewer-prompt.md`

Прекратить делегирование в `requesting-code-review/code-reviewer.md`. Проверяющий качества задачи получает собственный ограниченный шаблон:

- **Постановка:** «Вы проверяете качество реализации одной задачи». Это проверка задачи, а не готовности к слиянию.
- **Соответствие спецификации уже установлено:** соответствующая проверка прошла; не пересматривать требования и соответствие плану заново.
- **Сохраняемые аспекты:** качество кода — ясность, дублирование, обработка ошибок; качество тестов — проверка реального поведения, а не только моков; сопровождаемость; существующие SDD-проверки единой ответственности, независимой тестируемости, структуры файлов по плану и роста файлов, вызванного изменением. Исключаются соответствие плану, безопасность, масштабируемость, готовность к эксплуатации и вывод о слиянии.
- **Ограничение охвата:** начать с `git diff BASE..HEAD`, сначала читать изменённые файлы, соседний код изучать только для оценки конкретно названного риска. Сквозные изменения — порядок блокировок, изменённые контракты функций и API, общее изменяемое состояние — являются законными рисками, оправдывающими проверку мест вызова. По умолчанию не обходить всю кодовую базу.
- **Ограничение тестов:** применять общий принцип. Не запускать наборы пакета целиком, детекторы гонок и многократные прогоны, пока не назван конкретный подозреваемый нестабильный тест или гонка. Иначе рекомендовать тяжёлую проверку в отчёте, а не запускать. Предупреждения и лишний вывод в результатах тестов исполнителя — замечания: вывод должен быть чистым; исполнитель тоже проверяет это при самопроверке.
- **Правило доказательств:** на каждый пункт «Что проверить» отвечать ссылкой файл:строка, а не голым да/нет. Добавлено после реальных оценок, где проверяющие давали неподтверждённое «да» на проверку доступного имени и очистки временной папки, хотя дефекты находились в проверяемом diff.
- **Только чтение:** сохранить краткое правило не изменять рабочее дерево, индекс, HEAD и состояние ветки. Инструкцию `git worktree add` из текущих шаблонов не переносить: ограниченному diff ревью не нужна копия другой ревизии. Та же причина действует для очистки запроса проверки спецификации ниже.
- **Вывод:** сильные стороны / замечания Critical, Important, Minor / «Task quality: Approved | Needs fixes».

### 2. Очистка `skills/subagent-driven-development/spec-reviewer-prompt.md`

- Удалить инструкцию `git worktree add`. Правило только чтения остаётся: ревью спецификации по diff не требует другой ревизии.
- Разрешить противоречие между требованием читать только diff и «проверять всё независимо»: соответствие определяется чтением diff по требованиям, а TDD-доказательства исполнителя подтверждают запуск. Применяется общий принцип тестов.
- Добавить третий канал вывода для требований, которые нельзя проверить по diff, например они находятся в неизменённом коде или охватывают несколько задач: «⚠️ Cannot verify from diff — controller should check X». Это лучше обхода всего проекта или молчаливого одобрения. В бинарной схеме pass/fail нет пути для такого состояния, поэтому инструкции контроллера в разделе 3 определяют обработку: ⚠️ не блокирует запуск проверяющего качества, но до завершения задачи контроллер обязан самостоятельно разрешить каждый пункт, поскольку у него есть план и межзадачный контекст. Подтверждённый пробел считается провалом проверки спецификации и возвращается исполнителю.
- Заменить выдуманную предпосылку «исполнитель завершил работу подозрительно быстро» обоснованным скепсисом: воспринимать отчёт исполнителя как неподтверждённые утверждения о коде. Уровень проверки тот же, выдуманного факта нет.

### 3. Изменения контроллера в `skills/subagent-driven-development/SKILL.md`

- **Выбор модели:** заменить правило «для архитектуры, проектирования и ревью использовать наиболее сильную модель» рекомендацией выбирать модель проверяющего так же осмысленно, как модель исполнителя, с учётом размера, сложности и риска diff. Уточнить, что список сигналов сложности задачи относится к реализации; выбор проверяющего основан на том же суждении, поэтому узкое ревью diff не превращается автоматически в «понимание всей кодовой базы → самая сильная модель».
- **Составление запроса проверяющему:** рядом с Red Flags добавить указания: не давать открытых требований вроде «проверь все использования» или «запусти тесты гонок, если полезно» без конкретной причины, связанной с задачей; не просить повторно выполнять тесты исполнителя на том же коде; не решать за проверяющего, какие замечания игнорировать, — подозрение на ложный результат разрешать в цикле проверки; проверка отдельной задачи ограничена задачей, широкая проверка выполняется один раз для всей ветки в конце. Запрет предварительного решения добавлен после реального запуска, где контроллер выдумал утверждение «план запрещает общий вспомогательный код» и велел проверяющему не отмечать намеренно внесённое нарушение DRY.
- Контроллер также обязан передавать в требованиях общие ограничения спецификации или проекта, относящиеся к задаче: минимальные версии, правила имён и текста, требования платформ. В одном запуске модуль с минимумом `go 1.26.1` прошёл вопреки проектному требованию «Go 1.21+», потому что ни один проверяющий не увидел ограничение. Модель нужно явно указывать в каждом запуске: иначе наследуется модель сеанса, обычно самая дорогая, и выбор модели незаметно теряет смысл.
- **Обработка ⚠️ от проверяющего спецификации:** рядом с обработкой статусов исполнителя добавить правило самостоятельно разрешать каждый пункт «невозможно проверить по diff» до завершения задачи; подтверждённые пробелы возвращать исполнителю как провал проверки спецификации.
- **Явно сохранить широкую финальную проверку:** добавить в узел запуска итогового проверяющего прямую ссылку `../requesting-code-review/code-reviewer.md`. Сейчас этот шаблон доступен только через делегирование из запроса качества отдельной задачи; без новой ссылки после удаления делегирования шаблон остался бы без входящей ссылки. Уточнить в Integration, что `superpowers:requesting-code-review` предоставляет шаблон проверяющего только для итогового ревью.
- **Пример процесса:** обновить строки проверяющего качества под новый словарь вывода «Task quality: Approved»; строку итогового проверяющего о готовности к слиянию сохранить.
- Топология схемы не меняется: канал ⚠️ обрабатывается инструкциями контроллера, а не новой веткой схемы.

## Известное отложенное ограничение

Проверяющий спецификации сверяет результат с текстом задачи, который передал контроллер; он не может заметить требования, потерянные контроллером при извлечении из плана. Это архитектурное свойство схемы «контроллер передаёт полный текст», а не проблема формулировки запроса; в данную задачу исправление не входит.

- Существующие тесты инфраструктуры плагина `tests/` проходят.
- Запустить оценки поведения SDD до и после изменения: `git submodule update --init evals`, затем инструкции `evals/README.md`. В частности, `sdd-go-fractals`, `sdd-svelte-todo`, `sdd-rejects-extra-features` — сквозной SDD с проверкой YAGNI проверяющим спецификации — и `spec-reviewer-catches-planted-flaws`.
