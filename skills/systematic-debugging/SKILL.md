# Системная отладка

## Обзор

**Главный принцип:** ВСЕГДА находи первопричину до попытки исправления. Исправление симптомов не решает проблему.

**Нарушить букву процесса — значит нарушить и сам принцип отладки.**

## Непреложное правило

```text
НИКАКИХ ИСПРАВЛЕНИЙ БЕЗ ПРЕДВАРИТЕЛЬНОГО ПОИСКА ПРИЧИНЫ
```

Пока этап 1 не завершён, нельзя предлагать исправления.

## Когда применять

Для ЛЮБОЙ технической проблемы:
- Сбои тестов.
- Ошибки в production.
- Неожиданное поведение.
- Проблемы производительности.
- Ошибки сборки.
- Проблемы интеграции.

**ОСОБЕННО применяй, когда:**
- Время поджимает: в аварийной ситуации легко начать угадывать.
- Кажется очевидным «одно быстрое исправление».
- Уже испробовано несколько исправлений.
- Предыдущее исправление не сработало.
- Ты не до конца понимаешь проблему.

**Не пропускай, когда:**
- Проблема кажется простой: у простых ошибок тоже есть причины.
- Ты спешишь: спешка приводит к переделкам.
- Руководитель требует исправить СЕЙЧАС: системный подход быстрее беспорядочных попыток.

## Четыре этапа

Каждый этап ОБЯЗАТЕЛЬНО завершить до перехода к следующему.

### Этап 1: поиск первопричины

**ДО ЛЮБОЙ попытки исправления:**

1. **Внимательно прочитай сообщения об ошибках.** Не пропускай ошибки и предупреждения: они часто содержат точное решение. Прочитай трассировку стека целиком, отметь номера строк, пути файлов и коды ошибок.
2. **Добейся устойчивого воспроизведения.** Можно ли надёжно вызвать ошибку? Каковы точные шаги? Происходит ли она каждый раз? Если воспроизвести нельзя — собери дополнительные данные, не угадывай.
3. **Проверь недавние изменения.** Что могло вызвать проблему? Изучи git diff, последние коммиты, новые зависимости, изменения конфигурации и различия окружения.
4. **Собери доказательства в многокомпонентной системе.** Если система состоит из нескольких компонентов — например, CI → сборка → подпись или API → сервис → база, — перед предложением исправления добавь диагностику:

   ```text
   Для КАЖДОЙ границы между компонентами:
     - Зафиксируй, какие данные входят в компонент
     - Зафиксируй, какие данные выходят
     - Проверь передачу окружения и конфигурации
     - Проверь состояние на каждом уровне

   Выполни один раз, чтобы получить доказательства, ГДЕ возникает сбой
   ЗАТЕМ проанализируй доказательства и найди проблемный компонент
   ЗАТЕМ исследуй именно этот компонент
   ```

   **Пример многоуровневой системы:**
   ```bash
   # Уровень 1: процесс
   echo "=== Секреты, доступные процессу: ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # Уровень 2: скрипт сборки
   echo "=== Переменные окружения в скрипте сборки: ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY присутствует в окружении" || echo "IDENTITY отсутствует в окружении"

   # Уровень 3: скрипт подписи
   echo "=== Состояние связки ключей: ==="
   security list-keychains
   security find-identity -v

   # Уровень 4: сама подпись
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **Это показывает**, на каком уровне возникает сбой: секреты → процесс ✓, процесс → сборка ✗.

5. **Проследи поток данных.** Если ошибка глубоко в стеке вызовов, полная методика обратной трассировки находится в `root-cause-tracing.md` рядом с этим файлом.

   Кратко: откуда взялось неверное значение? Кто вызвал функцию с ним? Продолжай двигаться назад до источника. Исправляй источник, а не симптом.

### Этап 2: анализ работающего образца

**Найди закономерность до исправления:**

1. **Найди рабочие примеры.** Где в этом же проекте работает похожий код? Что именно работает в похожем случае?
2. **Сравни с эталоном.** При реализации шаблона прочитай эталонную реализацию ЦЕЛИКОМ, каждую строку. Полностью пойми подход до его применения.
3. **Определи различия.** Перечисли все отличия рабочего случая от сломанного, даже мелкие. Не предполагай, что они не могут иметь значения.
4. **Разберись с зависимостями.** Какие компоненты, настройки, конфигурация и окружение нужны? Какие предположения сделаны?

### Этап 3: гипотеза и проверка

**Научный метод:**

1. **Сформулируй одну гипотезу.** Чётко запиши: «Я считаю первопричиной X, потому что Y». Избегай расплывчатости.
2. **Проверь минимальным изменением.** Измени МИНИМУМ, необходимый для проверки. За раз меняй одну переменную, а не несколько вещей.
3. **Проверь результат до продолжения.** Сработало? Да → этап 4. Нет → сформулируй НОВУЮ гипотезу. НЕ наслаивай новые исправления.
4. **Если не знаешь.** Скажи «Я не понимаю X», не притворяйся знающим, попроси помощи и изучи вопрос глубже.

### Этап 4: реализация

**Исправляй первопричину, а не симптом:**

1. **Создай тест, который падает.** Минимально воспроизведи проблему: автоматическим тестом, если возможно, или одноразовым тестовым скриптом при отсутствии системы тестирования. Тест ОБЯЗАТЕЛЕН до исправления. Для правильного создания падающих тестов используй `superpowers:test-driven-development`.
2. **Внеси одно исправление.** Устрани выявленную первопричину. Одно изменение за раз. Не добавляй улучшения «раз уж я здесь» и не объединяй их с рефакторингом.
3. **Проверь исправление.** Тест теперь проходит? Другие тесты не сломаны? Проблема действительно устранена? Перед заявлением об успехе используй `superpowers:verification-before-completion`.
4. **Если исправление не сработало:**
   - ОСТАНОВИСЬ.
   - Посчитай, сколько исправлений уже испробовано.
   - Если меньше 3 — вернись к этапу 1 и заново проанализируй проблему с учётом новых данных.
   - **Если 3 или больше — ОСТАНОВИСЬ и пересмотри архитектуру, как указано в пункте 5.**
   - НЕ пробуй четвёртое исправление без обсуждения архитектуры.
5. **Если три или более исправлений не сработали — пересмотри архитектуру.**

   Признаки архитектурной проблемы:
   - Каждое исправление обнаруживает новое общее состояние, связанность или проблему в другом месте.
   - Для исправлений требуется масштабный рефакторинг.
   - Каждое исправление вызывает новые симптомы в другом месте.

   **ОСТАНОВИСЬ и проверь основы:**
   - Верен ли сам подход?
   - Не держимся ли мы за него просто по инерции?
   - Стоит ли изменить архитектуру вместо дальнейшего исправления симптомов?

   **Обсуди с пользователем до новых попыток.** Это не просто неудачная гипотеза: возможно, неверна архитектура.

## Тревожные признаки — ОСТАНОВИСЬ и следуй процессу

Если ловишь себя на мыслях:
- «Сейчас быстро исправлю, исследую потом».
- «Попробую изменить X и посмотрю».
- «Внесу несколько изменений и запущу тесты».
- «Пропущу тест и проверю вручную».
- «Наверное, причина в X, исправлю».
- «Я не всё понимаю, но это может сработать».
- «В образце X, но я сделаю иначе».
- «Вот основные проблемы» — затем перечислены исправления без исследования.
- Предлагаешь решение до трассировки потока данных.
- **«Ещё одна попытка исправления» после двух или более попыток.**
- **Каждое исправление обнаруживает новую проблему в другом месте.**

**Всё это означает: ОСТАНОВИСЬ. Вернись к этапу 1.**

**Если не сработали три и более исправления:** пересмотри архитектуру, этап 4, пункт 5.

## Сигналы пользователя, что подход неверен

Обрати внимание на такие реплики:
- «Разве это не происходит?» — ты сделал предположение без проверки.
- «Это покажет нам…?» — следовало собрать доказательства.
- «Перестань гадать» — ты предлагаешь исправление без понимания.
- «Подумай глубже» — пересмотри основы, а не только симптомы.
- «Мы застряли?» — подход не работает.

**При этих сигналах:** ОСТАНОВИСЬ. Вернись к этапу 1.

## Типичные оправдания

| Оправдание | Реальность |
|---|---|
| «Проблема простая, процесс не нужен» | У простых ошибок тоже есть первопричины; процесс для них быстр. |
| «Авария, нет времени на процесс» | Системная отладка БЫСТРЕЕ хаотичных догадок. |
| «Сначала попробую это, потом исследую» | Первое исправление задаёт подход. Сразу делай правильно. |
| «Напишу тест, когда подтвержу исправление» | Непроверенные исправления ненадёжны. Сначала тест доказывает проблему. |
| «Несколько исправлений сразу экономят время» | Невозможно понять, что сработало; могут появиться новые ошибки. |
| «Эталон слишком длинный, адаптирую по ходу» | Неполное понимание порождает ошибки. Прочитай целиком. |
| «Я вижу проблему, дайте исправить» | Видеть симптомы ≠ понимать первопричину. |
| «Ещё одна попытка» после двух и более неудач | Три и более неудач указывают на архитектурную проблему. Пересмотри подход. |

## Краткая справка

| Этап | Основные действия | Критерий успеха |
|---|---|---|
| **1. Первопричина** | Прочитать ошибки, воспроизвести, проверить изменения, собрать доказательства | Понятно, ЧТО и ПОЧЕМУ произошло |
| **2. Образец** | Найти работающие примеры, сравнить | Различия установлены |
| **3. Гипотеза** | Сформулировать версию, минимально проверить | Гипотеза подтверждена или сформирована новая |
| **4. Реализация** | Создать тест, исправить, проверить | Ошибка устранена, тесты проходят |

## Если процесс выявил «отсутствие первопричины»

Если системное исследование показало, что проблема действительно связана с окружением, временем или внешней системой:

1. Процесс завершён.
2. Запиши, что было исследовано.
3. Реализуй подходящую обработку: повтор, таймаут или сообщение об ошибке.
4. Добавь мониторинг и журналирование для будущего исследования.

**Но:** по оценке автора, 95% случаев «без первопричины» — незавершённое исследование.
