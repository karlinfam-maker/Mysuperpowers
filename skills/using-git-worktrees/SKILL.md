# Использование Git Worktrees

## Обзор

Убедись, что работа ведётся в изолированной рабочей области. Предпочитай встроенные инструменты платформы для worktree. Используй ручной git worktree только при отсутствии встроенного инструмента.

**Главный принцип:** сначала проверь существующую изоляцию, затем используй встроенные инструменты и только затем — git. Не обходи средства рабочей среды.

**Объяви в начале:** «Использую навык using-git-worktrees, чтобы подготовить изолированную рабочую область».

## Шаг 0: проверь существующую изоляцию

**Прежде чем что-либо создавать, проверь, не находишься ли ты уже в изолированной рабочей области.**

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
```

**Проверка субмодуля:** условие `GIT_DIR != GIT_COMMON` выполняется и внутри субмодулей git. Прежде чем заключить, что ты уже в worktree, убедись, что это не субмодуль:

```bash
# Если команда возвращает путь, это субмодуль, а не worktree: считай его обычным репозиторием
git rev-parse --show-superproject-working-tree 2>/dev/null
```

**Если `GIT_DIR != GIT_COMMON` и это не субмодуль:** ты уже в связанном worktree. Переходи к шагу 2, подготовке проекта. НЕ создавай ещё один worktree.

Сообщи состояние ветки:
- Если находишься в ветке: «Уже работаю в изолированной рабочей области `<path>`, ветка `<name>`».
- Если HEAD отсоединён: «Уже работаю в изолированной рабочей области `<path>`; HEAD отсоединён и управляется извне. При завершении потребуется создать ветку».

**Если `GIT_DIR == GIT_COMMON` или это субмодуль:** ты находишься в обычной рабочей копии репозитория.

Пользователь уже указал предпочтения по worktree в инструкциях? Если нет, до создания спроси согласие:

> «Создать изолированную рабочую область? Это защитит текущую ветку от изменений».

Соблюдай ранее выраженные предпочтения, не спрашивая повторно. Если пользователь не согласен, работай в текущей области и переходи к шагу 2.

## Шаг 1: создай изолированную область

**Есть два способа. Пробуй их в указанном порядке.**

### 1а. Встроенные инструменты worktree — предпочтительно

Пользователь попросил изолированную область или согласился на шаге 0. Проверь, есть ли способ создать worktree: инструмент вроде `EnterWorktree`, `WorktreeCreate`, команда `/worktree` или параметр `--worktree`. Если есть, используй его и переходи к шагу 2.

Встроенные инструменты сами управляют размещением каталога, созданием ветки и очисткой. Вызов `git worktree add` при наличии встроенного инструмента создаёт состояние, которое рабочая среда может не видеть и не контролировать.

Переходи к шагу 1б, только если встроенный инструмент недоступен.

### 1б. Резервный способ: Git Worktree

**Используй только когда шаг 1а неприменим**, то есть встроенного инструмента нет. Создай worktree вручную через git.

#### Выбор каталога

Соблюдай порядок приоритета. Явное предпочтение пользователя всегда важнее обнаруженного состояния файловой системы.

1. **Проверь инструкции на предпочтительный каталог worktree.** Если пользователь его уже указал, используй без повторного вопроса.
2. **Проверь существующий каталог внутри проекта:**
   ```bash
   ls -d .worktrees 2>/dev/null     # Предпочтительный скрытый каталог
   ls -d worktrees 2>/dev/null      # Альтернатива
   ```
   Используй найденный каталог. Если есть оба, выбирай `.worktrees`.
3. **Если других указаний нет**, по умолчанию используй `.worktrees/` в корне проекта.

#### Проверка безопасности для каталогов внутри проекта

**ОБЯЗАТЕЛЬНО убедись до создания worktree, что каталог игнорируется:**

```bash
git check-ignore -q .worktrees 2>/dev/null || git check-ignore -q worktrees 2>/dev/null
```

**Если каталог НЕ игнорируется:** добавь его в .gitignore, создай коммит и продолжай.

**Почему это важно:** проверка предотвращает случайное включение содержимого worktree в репозиторий.

#### Создание worktree

```bash
# Определи путь по выбранному расположению
path="$LOCATION/$BRANCH_NAME"

git worktree add "$path" -b "$BRANCH_NAME"
cd "$path"
```

**Если песочница блокирует создание:** когда `git worktree add` завершилась ошибкой доступа, сообщи пользователю, что создание заблокировано песочницей и работа продолжится в текущем каталоге. Затем подготовь проект и запусти исходные тесты на месте.

## Шаг 2: подготовь проект

Автоматически определи и выполни подходящую подготовку:

```bash
# Node.js
if [ -f package.json ]; then npm install; fi

# Rust
if [ -f Cargo.toml ]; then cargo build; fi

# Python
if [ -f requirements.txt ]; then pip install -r requirements.txt; fi
if [ -f pyproject.toml ]; then poetry install; fi

# Go
if [ -f go.mod ]; then go mod download; fi
```

## Шаг 3: проверь исходное состояние

Запусти тесты, чтобы убедиться в чистом исходном состоянии:

```bash
# Выбери команду, соответствующую проекту
npm test / cargo test / pytest / go test ./...
```

**Если тесты не проходят:** сообщи о сбоях и спроси, продолжать ли работу или исследовать их.

**Если тесты проходят:** сообщи о готовности.

## Краткая справка

| Ситуация | Действие |
|---|---|
| Уже находишься в связанном worktree | Пропусти создание, шаг 0 |
| Находишься в субмодуле | Считай его обычным репозиторием, проверка шага 0 |
| Есть встроенный инструмент worktree | Используй его, шаг 1а |
| Встроенного инструмента нет | Резервный способ git worktree, шаг 1б |
| Есть `.worktrees/` | Используй его, проверив игнорирование |
| Есть `worktrees/` | Используй его, проверив игнорирование |
| Есть оба | Используй `.worktrees/` |
| Ни одного нет | Проверь инструкции, затем выбери `.worktrees/` по умолчанию |
| Каталог не игнорируется | Добавь в .gitignore и создай коммит |
| Ошибка доступа при создании | Работай на месте согласно резервному сценарию |
| Исходные тесты не проходят | Сообщи о сбоях и спроси |
| Нет package.json/Cargo.toml | Пропусти установку зависимостей |

## Типичные оправдания

| Оправдание | Реальность |
|---|---|
| «Я явно не в worktree — проверять не надо» | Выполни шаг 0. Изоляцию среды и субмодули легко не заметить; команды проверки установят факты. |
| «`git worktree add` быстрее, чем искать встроенный инструмент» | Встроенный инструмент, например `EnterWorktree`, управляет размещением, веткой и очисткой. Его обход — главная ошибка: появляется состояние, которое среда не видит и не контролирует. |
| «Каталог worktree наверняка уже игнорируется» | Выполни `git check-ignore`. Неигнорируемый каталог может попасть в репозиторий целиком. |
| «Подойдёт любое имя каталога» | Явные инструкции важнее существующего каталога проекта, а он важнее `.worktrees/` по умолчанию. |
| «Рабочая область свежая, исходные тесты подождут» | При грязном исходном состоянии причина будущих сбоев будет неясна. Запусти тесты сейчас; продолжать ли при ошибках, решает пользователь. |
