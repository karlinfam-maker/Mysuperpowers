# Как писать хорошие тесты

**Загружай этот справочник, когда:** пишешь или изменяешь тесты, добавляешь имитации — mocks — либо вспомогательные методы и очистку для тестов.

## Обзор

Тест существует, чтобы обнаруживать конкретную поломку. Два принципа управляют всем остальным:

```text
1. Каждый тест называет поломку, которую он обнаруживает
2. Каждый тест проверяет реальное поведение
```

Строгий TDD естественно обеспечивает оба принципа: тест, написанный первым и увиденный падающим на реальном коде, уже доказал способность обнаружить ошибку. Имитация вводится, когда настоящая зависимость оказалась медленной или внешней.

## Принцип 1: назови поломку

До написания тела теста ответь: **какое изменение production-кода должно сломать тест и будет ли оно ошибкой или осознанным решением?** Тест оправдан, если выявляет неверную ветку, пропущенный побочный эффект, неправильный аргумент, граничный случай или нарушение контракта.

**Получай ожидаемые значения независимо.** Используй буквальные значения и проверенные вручную входные данные; предпочтительны табличные тесты с конкретными значениями `want`. Ожидание, вычисленное самим проверяемым кодом или его помощниками, пройдёт независимо от его поведения:

```typescript
// ❌ Mirror assertion: the same builder computes both sides — always true
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ Hand-derived literal
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**Не пиши детекторы изменений.** Если тест падает только из-за намеренного решения — значения константы, точной формулировки сообщения или внутренней структуры, — он реагирует на переработку, но пропускает ошибки. Проверяй поведение, зависящее от решения: не `expect(MAX_RETRIES).toBe(5)`, а «неудачный вызов повторяется пять раз и шестой попытки нет».

**Поведение, а не текст.** Проверка наличия точной строки в скрипте, навыке или конфигурации доказывает только наличие строки. Запускай скрипты с контролируемыми входными данными и проверяй вывод, побочные эффекты или код выхода. Документы с инструкциями агенту проверяются по поведению использующего их агента — `superpowers:writing-skills`; обычный текст для людей сам по себе тестов не требует.

**Твой код, а не фреймворк.** Проверяй контракт своего кода на границе: зарегистрированный маршрут, сформированный запрос, созданную полезную нагрузку. Внутреннюю механику стороннего инструмента проверяют его авторы. Например, тест того, что роутер вызывает зарегистрированный обработчик, относится к фреймворку. Если поведение зависимости действительно удивило, напиши один узкий тест, фиксирующий предположение. То же внутри проекта: конструкторы, геттеры, константы и простая передача вызова требуют тестов, если проверяют, нормализуют, устанавливают значение по умолчанию, выводят значение, обеспечивают правило или создают побочный эффект. Иначе проверяй первый видимый потребителю результат, который от них зависит.

### Контроль перед тестом

```text
ДО написания тела теста:
  Назови изменение production-кода, из-за которого он должен упасть.

  Не получается назвать       → перестрой тест вокруг наблюдаемого поведения
  «Изменился текст исходника» → запусти результат и проверь его последствия
  Только осознанные решения   → это детектор изменений; проверь поведение,
                                 зависящее от решения

  Убедись, что ожидаемое значение получено без проверяемого кода.
  ЕСЛИ оно повторяет его логику или использует его помощников:
    Замени конкретным значением или проверенным вручную примером
```

## Принцип 2: проверяй реальное поведение

**Не проверяй существование имитации вместо компонента.** Проверка имитации проходит, когда она есть, и падает, когда её нет; о компоненте это ничего не говорит. Проверяй поведение реального компонента. Если проверяешь саму имитацию, убери её или убери такую проверку.

```typescript
// ✅ Real behavior
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ Mock existence
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**Вопрос пользователя:** «Мы проверяем поведение имитации?»

**Подменяй зависимость на правильном уровне.** До замены изучи все побочные эффекты реального метода; подмени медленную или внешнюю операцию, а всё, от чего зависит тест, оставь настоящим. При сомнении сначала запусти тест с реальной реализацией и посмотри, что действительно происходит.

```typescript
// ❌ The mock swallows the config write that duplicate detection reads
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ Mock only the slow server startup; the config write stays real
vi.mock('MCPServerManager');
```

**Делай тестовые замены конкретными.** Если аргументы, число вызовов или порядок входят в контракт, проверяй их: заглушка, принимающая всё, ничего не подтверждает. Для каждой ветки — успех, ошибка, неверный формат — используй отдельный пример или spy, чтобы неверная ветка не могла удовлетворить ожидание.

**Полностью воспроизводи реальные данные.** Имитация должна включать всю фактическую документированную структуру, а не только поля, которые читает текущий тест. Частичная имитация может незаметно пропустить отсутствующее поле: тест пройдёт, а интеграция сломается.

**В production-классах только production-методы.** Очистку, нужную лишь тестам, помещай в тестовые утилиты, а не в `destroy()` рабочего класса. Спроси: вызывается ли метод только тестами? Управляет ли класс жизненным циклом ресурса? Если ответственность не принадлежит классу, используй тестовую утилиту.

**Предпочитай реальные компоненты сложным имитациям.** Если настройка имитаций больше логики теста, в них отсутствуют методы реальных компонентов или тест ломается при изменении имитации, переходи к интеграционному тесту с реальными компонентами. **Вопрос пользователя:** «Нужна ли здесь вообще имитация?»

### Контроль перед имитацией

```text
ДО добавления имитации или тестового помощника:
  Перечисли побочные эффекты реального метода; сохрани настоящими те,
  от которых зависит тест. Подменяй более глубокий медленный или внешний слой.

  Ответы имитации полностью повторяют реальную структуру.

  Метод, вызываемый только тестами, находится в тестовых утилитах,
  а не в production-коде.

  Собираешься проверять саму имитацию?
    Убери подмену или убери такую проверку.
```

## Тесты выпускаются вместе с реализацией

Цикл TDD — падающий тест, минимальная реализация, рефакторинг — определяет завершённость работы. Добавляй нужные для поведения тесты и только их: тривиальному коду и обычному тексту для людей тесты могут не требоваться, а тест ради процесса создаёт постоянные затраты на поддержку.

## Проверка мутациями

Перед завершением мысленно измени production-код. Для каждого реалистичного изменения должен упасть хотя бы один тест:

- Неверная константа или аргумент.
- Неверный обработчик ветки.
- Пропущенное изменение состояния или побочный эффект.
- Пустой результат или значение по умолчанию.
- Нет проверки нуля, пустого значения, nil, отсутствия прав или неверного формата.

Если изменение не обнаруживается, поведение не защищено либо тест тавтологичен.

## Краткая справка

| Когда ты… | Действие |
|---|---|
| Пишешь тест | Назови ошибку, которую он обнаруживает, а не осознанное изменение |
| Получаешь ожидаемое значение | Выведи его вручную, не используя проверяемый код |
| Проверяешь скрипт или документ | Запусти его или проверь поведение потребителя, а не ищи строку |
| Собираешься тестировать зависимость | Проверяй свой контракт на границе, не документированную механику зависимости |
| Хочешь проверить имитированный элемент | Проверь реальный компонент или убери подмену |
| Собираешься подменить метод | Изучи его побочные эффекты; подменяй медленный или внешний слой |
| Формируешь ответ имитации | Воспроизведи реальную структуру полностью |
| Нужна очистка только для тестов | Помести её в тестовые утилиты |
| Настройка имитаций разрастается | Используй интеграционный тест с реальными компонентами |
| Заканчиваешь файл тестов | Выполни мысленную проверку мутациями |

## Тревожные признаки

- Подготовка и проверка используют один объект, гарантируя равенство.
- Тест может упасть только из-за аварийного завершения, исключения или отсутствующего селектора.
- Тест падает при любом намеренном изменении, но не при случайной поломке.
- Ожидаемые значения скрыты за циклами, построителями или помощниками.
- Тест ищет текст исходника либо проверяет, что удалённый символ не вернулся.
- Тест оставался бы значимым, даже если бы кроме фреймворка ничего не существовало.
- Тест написан ради покрытия и не проверяет ни результата, ни побочного эффекта.
- Проверка использует test ID `*-mock` или падает при удалении имитации.
- Метод вызывается только из файлов тестов.
- Настройка имитаций занимает более половины теста или невозможно объяснить её необходимость.
- Имитация добавлена «на всякий случай».
