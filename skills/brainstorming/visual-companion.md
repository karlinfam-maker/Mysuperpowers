# Руководство по визуальному помощнику

Браузерный помощник для обсуждения идей: показывает макеты, схемы и варианты.

## Когда применять

Решай для каждого вопроса отдельно, а не для всей сессии. Критерий: **поможет ли показ понять вопрос лучше, чем текст?**

**Используй браузер**, если само содержание визуально:
- **Макеты интерфейса:** каркасы экранов, расположение элементов, навигация, компоненты.
- **Архитектурные схемы:** компоненты системы, потоки данных, связи.
- **Сравнение рядом:** два макета, цветовые схемы или направления дизайна.
- **Доработка дизайна:** внешний вид, интервалы, визуальная иерархия.
- **Пространственные связи:** диаграммы состояний, блок-схемы и связи сущностей.

**Используй терминал**, когда содержание текстовое или табличное:
- **Требования и границы:** «что означает X?», «какие функции входят?».
- **Концептуальный выбор A/B/C:** сравнение подходов словами.
- **Компромиссы:** преимущества и недостатки, таблицы сравнения.
- **Технические решения:** проектирование API, модели данных, архитектурные подходы.
- **Уточнения:** когда ответом служат слова, а не визуальное предпочтение.

Вопрос об интерфейсе не обязательно визуальный. «Какой мастер настройки нужен?» — концептуальный вопрос для терминала. «Какой из этих макетов мастера подходит?» — визуальный вопрос для браузера.

## Принцип работы

Сервер следит за каталогом HTML-файлов и отдаёт браузеру самый новый. Ты записываешь HTML в `screen_dir`; пользователь видит страницу и может выбирать варианты. Выбор записывается в `state_dir/events`, который читается на следующем ходе.

**Фрагменты или полные документы:** если HTML начинается с `<!DOCTYPE` или `<html`, сервер отдаёт его как есть, добавив вспомогательный скрипт. Иначе сервер автоматически оборачивает содержимое шаблоном: добавляет заголовок, тему CSS, состояние соединения и интерактивность. **По умолчанию пиши фрагменты.** Полный документ нужен только при необходимости полностью контролировать страницу.

## Запуск сессии

Запускай сервер после согласия пользователя на визуального помощника:

```bash
# Запускай ПОСЛЕ согласия пользователя. --open открывает браузер при первом
# экране; --project-dir сохраняет макеты и позволяет перезапускать сервер на том же порту.
bash scripts/start-server.sh --project-dir /path/to/project --open

# Возвращает: {"type":"server-started","port":52341,
#           "url":"http://localhost:52341/?key=ab12…",
#           "screen_dir":"/path/to/project/.superpowers/brainstorm/12345-1706000000/content",
#           "state_dir":"/path/to/project/.superpowers/brainstorm/12345-1706000000/state"}
```

Сохрани `screen_dir` и `state_dir` из ответа. С `--open` браузер откроется при появлении первого экрана; отдельно просить пользователя открыть его не нужно. Но передай URL на случай, если автоматическое открытие недоступно, например в удалённой среде.

**URL содержит ключ сессии (`?key=…`).** Сервер отклоняет запросы без него, поэтому передавай пользователю **полный URL** из поля `url`: не удаляй строку запроса и не передавай голый `http://host:port`. Ключ защищает доступ по HTTP и WebSocket от посторонних вкладок или устройств сети. После первой загрузки браузер сохраняет ключ в cookie; перезагрузка и ресурсы `/files/*` работают без повторного указания.

**Как найти данные соединения:** сервер записывает начальный JSON в `$STATE_DIR/server-info`. Если сервер запущен в фоне и стандартный вывод не сохранён, прочитай файл и найди URL и порт. При использовании `--project-dir` каталог сессии находится в `<project>/.superpowers/brainstorm/`.

**Примечание:** передавай корень проекта как `--project-dir`, чтобы макеты сохранялись в `.superpowers/brainstorm/` и переживали перезапуск сервера. Без него файлы находятся в `/tmp` и очищаются. Напомни пользователю добавить `.superpowers/` в `.gitignore`, если его там ещё нет.

### Запуск для разных платформ

**Claude Code:** режим по умолчанию работает; скрипт сам переводит сервер в фон.

```bash
# Режим по умолчанию: скрипт сам переводит сервер в фон.
bash scripts/start-server.sh --project-dir /path/to/project --open
```

В Windows скрипт сам выбирает режим переднего плана, который блокирует вызов инструмента. Укажи `run_in_background: true` в вызове Bash, чтобы сервер пережил смену ходов, а на следующем ходе прочитай `$STATE_DIR/server-info` для URL и порта.

**Codex:** Codex завершает фоновые процессы. Скрипт определяет `CODEX_CI` и переходит на передний план; запусти обычным образом без дополнительных флагов.

```bash
# Codex завершает фоновые процессы. Скрипт определяет CODEX_CI и переходит
# на передний план. Запускай его обычно, без дополнительных флагов.
bash scripts/start-server.sh --project-dir /path/to/project --open
```

**Gemini CLI:** используй `--foreground` и укажи `is_background: true` в вызове оболочки, чтобы процесс пережил смену ходов.

```bash
# Используй --foreground и укажи is_background: true в вызове оболочки,
# чтобы процесс сохранялся между ходами.
bash scripts/start-server.sh --project-dir /path/to/project --open --foreground
```

**Copilot CLI:** запусти через неблокирующий или фоновый механизм оболочки Copilot CLI, сохранив `--foreground`, чтобы процессом управляла среда. Это файл `.sh`, поэтому вызывай его через bash; в Windows из PowerShell вызывай `bash.exe` Git Bash.

```bash
# Запусти через неблокирующий или фоновый механизм Copilot CLI, чтобы сервер
# сохранялся между ходами. Оставь --foreground для управления процессом средой.
# Файл .sh запускай через bash (в Windows из PowerShell вызывай bash.exe Git Bash).
bash scripts/start-server.sh --project-dir /path/to/project --open --foreground
```

**Другие среды:** сервер должен оставаться работающим между ходами. Если среда завершает отсоединённые процессы, используй `--foreground` и собственный механизм фонового выполнения платформы.

Если URL недоступен браузеру, что бывает в удалённых средах и контейнерах, привяжи сервер не только к loopback-интерфейсу:

```bash
bash scripts/start-server.sh \
  --project-dir /path/to/project \
  --host 0.0.0.0 \
  --url-host localhost
```

Параметр `--url-host` задаёт имя хоста, выводимое в JSON с URL.

## Цикл работы

1. **Проверь, что сервер работает**, и запиши HTML в новый файл `screen_dir`:
   - **Обязательно проверь сервер до передачи URL или нового экрана.** Убедись, что `$STATE_DIR/server-info` существует, а `$STATE_DIR/server-stopped` отсутствует. Если сервер остановился, запусти `start-server.sh` с тем же `--project-dir`: он повторно использует порт, открытая вкладка пользователя переподключится автоматически; пока сервер остановлен, показывается сообщение о паузе. Новый URL не нужен. После четырёх часов бездействия сервер завершается; интервал задаётся `--idle-timeout-minutes`.
   - Используй понятные имена: `platform.html`, `visual-style.html`, `layout.html`.
   - **Не используй одно и то же имя повторно:** каждому экрану нужен новый файл.
   - Используй инструмент создания файлов; исходная инструкция не рекомендует `cat` и heredoc, чтобы не засорять вывод терминала.
   - Сервер автоматически показывает самый новый файл.
2. **Объясни пользователю, что он увидит, и заверши ход:**
   - Напоминай URL на каждом шаге, а не только первом.
   - Кратко опиши экран: например, «Показываю три варианта главной страницы».
   - Попроси ответить в терминале: «Посмотри и скажи, что думаешь. При желании нажми на понравившийся вариант».
3. **На следующем ходе**, после ответа пользователя в терминале:
   - Прочитай `$STATE_DIR/events`, если файл есть: там взаимодействия в формате JSON по одной записи на строку.
   - Сопоставь их с текстовым ответом пользователя.
   - Основная обратная связь — сообщение в терминале; `state_dir/events` содержит структурированные действия.
4. **Повтори или двигайся дальше.** Если обратная связь меняет экран, создай новый файл, например `layout-v2.html`. Переходи к следующему вопросу только после проверки текущего.
5. **Убери устаревший экран при возврате в терминал.** Если следующий шаг не требует браузера — например, уточнение или обсуждение компромиссов, — покажи экран ожидания:

```html
   <!-- имя файла: waiting.html (или waiting-2.html и т. д.) -->
   <div style="display:flex;align-items:center;justify-content:center;min-height:60vh">
     <p class="subtitle">Продолжаем в терминале...</p>
   </div>
   ```

   Так пользователь не будет смотреть на уже решённый выбор, пока разговор перешёл дальше. Для следующего визуального вопроса создай новый файл.
6. Повторяй до завершения.

## Создание фрагментов

Пиши только содержимое страницы. Сервер сам добавляет шаблон с заголовком, темой CSS, состоянием соединения и интерактивностью.

**Минимальный пример:**

```html
<h2>Какой макет подходит лучше?</h2>
<p class="subtitle">Учитывайте читаемость и визуальную иерархию</p>

<div class="options">
  <div class="option" data-choice="a" onclick="toggleSelect(this)">
    <div class="letter">A</div>
    <div class="content">
      <h3>Одна колонка</h3>
      <p>Простое и удобное чтение</p>
    </div>
  </div>
  <div class="option" data-choice="b" onclick="toggleSelect(this)">
    <div class="letter">B</div>
    <div class="content">
      <h3>Две колонки</h3>
      <p>Боковая навигация и основное содержимое</p>
    </div>
  </div>
</div>
```

Этого достаточно: теги `<html>`, CSS и `<script>` не нужны — их предоставляет сервер.

## Доступные классы CSS

Шаблон страницы предоставляет следующие классы.

### Варианты A/B/C

```html
<div class="options">
  <div class="option" data-choice="a" onclick="toggleSelect(this)">
    <div class="letter">A</div>
    <div class="content">
      <h3>Название</h3>
      <p>Описание</p>
    </div>
  </div>
</div>
```

**Множественный выбор:** добавь `data-multiselect` к контейнеру. Каждый щелчок переключает выделение элемента.

```html
<div class="options" data-multiselect>
  <!-- та же разметка вариантов: можно выбирать несколько и отменять выбор -->
</div>
```

### Карточки визуальных вариантов

```html
<div class="cards">
  <div class="card" data-choice="design1" onclick="toggleSelect(this)">
    <div class="card-image"><!-- содержимое макета --></div>
    <div class="card-body">
      <h3>Название</h3>
      <p>Описание</p>
    </div>
  </div>
</div>
```

### Контейнер макета

```html
<div class="mockup">
  <div class="mockup-header">Просмотр: макет панели</div>
  <div class="mockup-body"><!-- HTML вашего макета --></div>
</div>
```

### Сравнение рядом

```html
<div class="split">
  <div class="mockup"><!-- слева --></div>
  <div class="mockup"><!-- справа --></div>
</div>
```

### Преимущества и недостатки

```html
<div class="pros-cons">
  <div class="pros"><h4>Преимущества</h4><ul><li>Плюс</li></ul></div>
  <div class="cons"><h4>Недостатки</h4><ul><li>Минус</li></ul></div>
</div>
```

### Элементы каркаса

```html
<div class="mock-nav">Логотип | Главная | О нас | Контакты</div>
<div style="display: flex;">
  <div class="mock-sidebar">Навигация</div>
  <div class="mock-content">Основное содержимое</div>
</div>
<button class="mock-button">Кнопка действия</button>
<input class="mock-input" placeholder="Поле ввода">
<div class="placeholder">Область заполнителя</div>
```

### Типографика и разделы

- `h2` — заголовок страницы.
- `h3` — заголовок раздела.
- `.subtitle` — дополнительный текст под заголовком.
- `.section` — блок с нижним отступом.
- `.label` — небольшая подпись прописными буквами.

## Формат событий браузера

При выборе в браузере действия записываются в `$STATE_DIR/events`: по одному JSON-объекту на строку. При показе нового экрана файл автоматически очищается.

```jsonl
{"type":"click","choice":"a","text":"Вариант A — простой макет","timestamp":1706000101}
{"type":"click","choice":"c","text":"Вариант C — сложная сетка","timestamp":1706000108}
{"type":"click","choice":"b","text":"Вариант B — гибрид","timestamp":1706000115}
```

Полная последовательность показывает, как пользователь изучал варианты: он может нажать несколько прежде, чем определиться. Последнее событие `choice` обычно отражает окончательный выбор, однако последовательность может показать сомнения или предпочтения, о которых стоит спросить.

Если `$STATE_DIR/events` отсутствует, пользователь не взаимодействовал с браузером; опирайся только на ответ в терминале.

## Советы по дизайну

- **Соответствие детализации вопросу:** для структуры достаточно каркаса; для обсуждения внешнего вида нужна более точная проработка.
- **Объясняй вопрос на каждой странице:** «Какой макет выглядит профессиональнее?», а не просто «Выбери один».
- **Уточняй до перехода дальше:** если отзыв меняет экран, создай новую версию.
- **Максимум 2–4 варианта** на экран.
- **Используй реальные материалы, когда это важно:** например, реальные изображения для портфолио фотографа. Заглушки могут скрывать проблемы дизайна.
- **Сохраняй простоту макетов:** сосредоточься на расположении и структуре, а не на пиксельной точности.

## Имена файлов

- Используй понятные имена: `platform.html`, `visual-style.html`, `layout.html`.
- Не повторяй имя: каждому экрану нужен новый файл.
- Для итераций добавляй версию: `layout-v2.html`, `layout-v3.html`.
- Сервер показывает новейший файл по времени изменения.

## Завершение

```bash
bash scripts/stop-server.sh $SESSION_DIR
```

При использовании `--project-dir` файлы макетов сохраняются в `.superpowers/brainstorm/` для последующего обращения. При остановке удаляются только временные сессии в `/tmp`.

## Справочные файлы

- Шаблон страницы и справка CSS: `scripts/frame-template.html`.
- Клиентский вспомогательный скрипт: `scripts/helper.js`.
