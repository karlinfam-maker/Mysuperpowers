# Переработка цикла исправлений SDD — проектная спецификация

**Статус:** проект утверждён после обсуждения с Jesse 2026-07-15; план реализации будет подготовлен отдельно.
**Цель:** сделать цикл проверки и исправлений навыка subagent-driven-development сходящимся и автономным, а документ — удобным для чтения, не переписывая формулировки, настроенные по результатам оценок.
**Жёсткое условие:** существующие настроенные по оценкам предложения можно переносить, но нельзя переформулировать. Новые механизмы сопровождаются результатами проверочных сценариев.

## Проблемы

Все четыре проблемы наблюдались в реальных сеансах:

1. **Бесконечные циклы проверки.** Цикл буквально предписывает «повторять до одобрения» без ограничения числа раундов. Каждая повторная проверка охватывает весь diff, поэтому недетерминированный проверяющий в каждом раунде находит новые замечания вместо проверки исправлений. Получается последовательность реализации, проверок и исправлений без механизма остановки. В спецификации strict-cost от 2026-06-10 число циклов независимо признано крупнейшим источником разброса стоимости между запусками.
2. **Противоречивая политика исправлений.** Схема процесса и раздел «Constructing Reviewer Prompts» направляют работу отдельным субагентам исправления; Red Flags требует, чтобы исправлял тот же исполнитель; раздел «After Review Findings» в implementer-prompt.md предполагает повторное привлечение исполнителя. На вопрос «кто исправляет?» один навык даёт три ответа.
3. **Разросшаяся структура.** Тринадцать разделов верхнего уровня; указания по одному действию разбросаны по четырём из них. В «Constructing Reviewer Prompts» смешаны инструкции проверяющему, политика исправлений, итоговое ревью и разрешение конфликтов плана.
4. **Формат Red Flags.** Семь других навыков используют таблицу рационализаций `| Excuse | Reality |`, а в SDD — список из 17 запретов и три небольших блока «Если X».

## Проектные решения

| № | Решение | Обоснование |
|---|---|---|
| 1 | Исправляет замечания первоначальный исполнитель: его сеанс возобновляется. | У него уже есть контекст задачи; ответственность за результат предпочтительнее случайного исправления. Новый субагент восстанавливает контекст для каждого замечания и не обладает общей картиной задачи. |
| 2 | Повторные проверки ограничены конкретными замечаниями. | Полная проверка при каждом раунде вызывает новые замечания и повторения. Ограниченная проверка делает цикл структурно сходящимся; итоговая проверка всей ветки остаётся общей защитой. |
| 3 | Ограничитель на пяти раундах: три возобновления прежнего исполнителя, затем два новых запуска более сильной модели. | Решение Jesse. Если три возобновления не помогли, исполнитель, вероятно, не видит собственной проблемы; новый более сильный исполнитель одновременно получает свежий взгляд и дополнительные возможности. |
| 4 | При достижении предела контроллер оценивает замечания и выбирает дальнейший путь. Новый этап согласования с человеком не вводится; структурные проблемы приводят к существующей остановке BLOCKED. | SDD предназначен для автономного выполнения. У контроллера есть контекст плана и зависимых задач, которого нет у проверяющего; действующий текст уже разрешает разрешать разногласия в цикле проверки, но не описывает механизм. |
| 5 | Перестроить SKILL.md по жизненному циклу, сохранив настроенные предложения. | Так устраняется причина сложности чтения. Правила переносятся туда, где применяются, что соответствует существующему подходу к документам. |
| 6 | Преобразовать Red Flags в таблицу рационализаций `| Excuse | Reality |`, а жёсткие правила перенести к месту применения. | Формат соответствует семи другим навыкам: оправдания получают опровержения, а правила соблюдаются в момент действия. |

## Цикл исправлений

**Условие запуска:** проверка задачи вернула несоответствие спецификации ❌ или замечание уровня Critical/Important.

**Раунды 1–3 — возобновление первоначального исполнителя.** Замечания передаются дословно: Critical/Important и пробелы в соответствии спецификации. Исполнитель исправляет проблему, повторно запускает покрывающие тесты, дописывает отчёт об исправлении в свой существующий файл и возвращает краткий отчёт установленного формата. В среде без возобновления агента «возобновлением» считается новый запуск с передачей задания, файла отчёта и замечаний: файл отчёта в любом случае служит постоянной памятью.

**Раунды 4–5 — новый исполнитель на более сильной модели.** Передаётся полный контекст: задание, файл отчёта, открытые замечания и пояснение «предыдущий исполнитель пытался решить задачу N раз; теперь ответственность за неё у вас».

**В каждом раунде повторная проверка ограничена исправлениями.** Проверяющий получает задание, обновлённый отчёт, первоначальный список замечаний и пакет diff исправления: `review-package FIX_BASE HEAD`, где FIX_BASE — последний просмотренный проверяющим head; скрипт уже поддерживает произвольные диапазоны. Он выносит решение по каждому замечанию — устранено или не устранено — и отмечает новые поломки только в diff исправления. Новые замечания к коду, который исправление не затронуло, сообщаются как неблокирующие; контроллер записывает их в журнал для итоговой проверки.

**Проверка полноты отчёта об исправлении:** существующее правило сохраняется. До повторной отправки проверяющему убедиться, что в отчёте указаны покрывающие тесты, запущенная команда и её вывод.

**Досрочный выход запрещён.** Контроллер не оценивает замечания самостоятельно до достижения предела: ранний выход снова открыл бы возможность заранее отвергать замечания ради экономии цикла, которую существующие инструкции намеренно исключают. Одно исключение сохраняется: если замечание противоречит тексту плана, вопрос немедленно передаётся человеку; это вопрос полномочий плана, а не повторения проверок.

**Незначительные замечания** в цикл не попадают: их записывают в журнал по мере поступления, как и раньше.

### Разрешение замечаний при достижении предела

Если пятый раунд не завершился успехом, контроллер прекращает отправлять задачи и оценивает каждое открытое замечание с учётом задания, плана и контекста других задач:

- **Спорное или ошибочное** → записать в журнал с кратким обоснованием, например «контроллер: проверяющий ошибается, потому что X», и продолжить. Итоговая проверка увидит обе позиции.
- **Реальное, но не определяющее дальнейшую работу** → записать как известное открытое замечание и продолжить. Последующие задачи, затрагивающие эту область, получают ссылку на запись.
- **Реальное и структурно важное** — например, от него зависят последующие задачи или оно указывает на дефект плана — → существующая остановка BLOCKED. Откладывание структурного сбоя позволяет зависимым задачам строиться на ошибке и переносит проблему на самый дорогой этап; поэтому выполнение останавливается существующим условием, без нового этапа согласования.

Каждое решение записывается в журнал. Молчаливо отбрасывать замечания по-прежнему запрещено.

## Перестройка документа

Новая структура в порядке выполнения:

1. Введение: зачем нужны субагенты, основной принцип, сообщения о ходе работы и непрерывное выполнение.
2. Когда использовать: без изменений, включая схему выбора.
3. Процесс: схема обновлена под новый цикл.
4. Подготовка: рабочая копия, проверка и возобновление журнала, предварительная проверка плана, список задач.
5. Выбор модели: остаётся одним общим разделом, поскольку к нему обращаются при каждом запуске; перенос к местам использования повторил бы содержание пять раз.
6. Цикл задачи из пяти шагов:
   1. Запустить исполнителя: скрипт task-brief, запрос из пяти частей, обязательная строка модели.
   2. Обработать отчёт: DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED.
   3. Проверить задачу: скрипт review-package, состав запроса проверяющему, проверка ограничений, запрет предварительно отвергать замечания, обработка ⚠️.
   4. Выполнить описанный выше цикл исправлений.
   5. Завершить задачу: дописать журнал и обновить список задач.
7. Итоговая проверка: пакет, назначение модели, одна волна исправлений, одна ограниченная повторная проверка и разрешение замечаний.
8. Завершение: finishing-a-development-branch.
9. Распространённые рационализации: таблица.
10. Пример процесса: обновлён так, чтобы показывать исправление через возобновление и случай, когда ограничитель не срабатывает.

Разделы «Constructing Reviewer Prompts», «File Handoffs» и «Durable Progress» распределяются между шагами, где применяются их правила. Каждое предложение, настроенное по результатам оценок, переносится ровно в одно новое место; план реализации содержит карту «источник → назначение», чтобы проверяющий убедился, что ничего не удалено и не переформулировано.

## Таблица рационализаций

Запреты, похожие на оправдания, превращаются в строки; новые строки охватывают патологический цикл. Черновые формулировки, окончательные определяются при реализации:

| Оправдание | Реальность |
|---|---|
| «Соответствие спецификации достаточно близкое» | Проверяющий нашёл пробелы — задача не завершена. |
| «Исправлю сам, запуск исполнителя — лишние затраты» | Исправления контроллера засоряют его контекст и обходят проверку. Возобновите исполнителя. |
| «Ещё один раунд точно завершится» | За пределом лимита цикл не сходится. Примите решение по замечаниям. |
| «Проверяющий всё равно найдёт что-нибудь новое» | Ограниченная повторная проверка проверяет исправления, а не вкусы. Новые замечания к нетронутому коду идут в журнал, а не в цикл. |
| «Это замечание явно неверно, отброшу его» | Самостоятельная оценка проводится только после лимита; каждое решение записывается в журнал. Молчаливое отбрасывание запрещено. |
| «Исправление небольшое, повторная проверка не нужна» | Именно непроверенные исправления приводят к регрессиям. |

Жёсткие правила, не являющиеся оправданиями, переносятся к местам применения: не запускать исполнителей параллельно, не отправлять проверяющего без файла diff, обязательно указывать модель, не отправлять повторно задачи, отмеченные в журнале завершёнными.

## Шаблоны запросов

- **implementer-prompt.md:** раздел «After Review Findings» переписывается под возобновление: исполнитель получит замечания, исправит их, повторно запустит покрывающие тесты, дополнит файл отчёта и вернёт краткий отчёт.
- **task-reviewer-prompt.md:** только первоначальная проверка; завершающее предложение о повторной проверке переносится.
- **re-review-prompt.md — новый:** ограниченная повторная проверка. На входе — задание, обновлённый отчёт, исходные замечания и пакет diff исправления. На выходе — решение по каждому замечанию, новые поломки в diff и неблокирующие наблюдения вне него. Отдельный шаблон нужен из-за другого контракта: совмещение с полным ревью породило текущую неоднозначность.
- **Передача новому исполнителю в раундах 4–5:** составляется из implementer-prompt.md и инструкций SKILL.md — задание, путь к отчёту, открытые замечания, объяснение передачи ответственности. Новый файл шаблона не нужен.

## Цикл итоговой проверки

Без изменений остаются пакет от merge-base, наиболее сильная модель и **один** исполнитель исправлений с полным списком замечаний. Новое правило: ровно одна ограниченная повторная проверка волны исправлений, затем решение контроллера по замечаниям. Оставшиеся структурно важные проблемы передаются на этап finishing-a-development-branch, где уже участвует человек. Таким образом, в конце ветки цикл тоже ограничен.

## Оценки

Три новых проверочных сценария в `evals/`:

1. **Возобновить, а не запускать нового:** проверка задачи возвращает замечания; контроллер обязан возобновить того же исполнителя, а не запускать отдельного субагента исправлений.
2. **Срабатывание ограничителя:** проверяющий намеренно остаётся неудовлетворённым; после неудачи пятого раунда контроллер прекращает отправки, оценивает замечания, записывает их в журнал и продолжает, а не зацикливается.
3. **Структурная проблема останавливает работу:** при замечании, от которого зависят последующие задачи, контроллер обязан остановиться через BLOCKED, а не отложить проблему.

Дополнительно — запуски существующих сценариев SDD до и после изменений для обнаружения регрессий из-за перестройки документа.

## Что не входит в цели

- Привязка журнала к сеансу: этим занимается PR #1943. Поскольку текущая работа затрагивает те же разделы, план реализации фиксирует риск конфликта.
- Изменения скриптов: task-brief и review-package уже выполняют необходимое для нового цикла.
- Изменения executing-plans или requesting-code-review, кроме сохранения работоспособной ссылки на итоговую проверку.
