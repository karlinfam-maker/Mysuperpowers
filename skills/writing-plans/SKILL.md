# Составление планов

## Приоритет правил проекта

В проектах Валерия правила СУИИР и его прямые указания имеют приоритет. Не требуй повторного подтверждения уже разрешённой работы и не приостанавливай её только из-за процесса Superpowers. Место плана определяй с учётом правил конкретного проекта и указаний пользователя.

## Обзор

Пиши план реализации для инженера, который не видел код проекта и спецификацию. Предполагай, что он умеет писать код в принятом в проекте стиле, если знает точный интерфейс и тест, и разумно выбирает там, где план оставляет свободу. Он не может знать принятые тобой решения: какие файлы, имена и сигнатуры использовать, какие значения взять из спецификации, какие тесты доказывают выполнение каждой задачи. Зафиксируй это. Разбей весь план на небольшие задачи. DRY. YAGNI. TDD. Частые коммиты.

**Объяви в начале:** «Использую навык writing-plans, чтобы подготовить план реализации».

**Контекст:** если работа выполняется в изолированном worktree, при выполнении плана он должен быть создан с помощью навыка `superpowers:using-git-worktrees`.

**По умолчанию сохраняй планы в:** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`.
- Предпочтения пользователя о месте плана важнее этого значения.

## Проверь границы

Если спецификация охватывает несколько независимых подсистем, при обсуждении идеи её следовало разделить на спецификации подпроектов. Если этого не сделали, предложи отдельный план для каждой подсистемы. Каждый план должен приводить к самостоятельному работающему и проверяемому результату.

## Структура файлов

До определения задач составь карту создаваемых и изменяемых файлов и их ответственности. Здесь фиксируется разбиение системы.

- Проектируй части с чёткими границами и определёнными интерфейсами. У каждого файла должна быть понятная ответственность.
- Код, целиком помещающийся в контекст, проще анализировать, а изменения в небольших целевых файлах надёжнее. Предпочитай их большим файлам, которые делают слишком много.
- Файлы, изменяемые вместе, должны находиться рядом. Разделяй по ответственности, а не по техническому слою.
- В существующем проекте соблюдай принятые подходы. Если файлы большие, не перестраивай проект в одностороннем порядке; однако если изменяемый файл стал слишком неудобным, можно предложить его разделение в плане.

Эта структура определяет разбиение на задачи. Каждая задача должна давать самостоятельное и понятное изменение.

## Размер задачи

Задача — минимальная единица с собственным циклом тестирования, которую имеет смысл передать отдельному проверяющему. Подготовку, настройки, создание заготовок и документацию включай в задачу, результату которой они нужны. Разделяй только там, где проверяющий может обоснованно отклонить одну задачу и принять соседнюю. Каждая задача завершается самостоятельно проверяемым результатом.

## Размер шага

**Каждый шаг — одно действие с проверяемым результатом:**
- «Написать падающий тест».
- «Запустить и убедиться, что он падает».
- «Написать минимум кода для прохождения теста».
- «Запустить тесты и убедиться, что они проходят».
- «Создать коммит».

## Заголовок документа плана

**Каждый план ОБЯЗАТЕЛЬНО начинается следующим заголовком:**

```markdown
# План реализации [Название функции]

> **Для агентов-исполнителей:** ОБЯЗАТЕЛЬНЫЙ НАВЫК: выполняй план по задачам через superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans. Для отслеживания шагов используй флажки (`- [ ]`).

**Цель:** [Одним предложением: что создаётся]

**Архитектура:** [2–3 предложения о подходе]

**Технологии:** [Основные технологии и библиотеки]

**Спецификация:** [путь к реализуемому документу: план опирается на него,
поэтому исполнитель читает оба документа]

## Общие ограничения

[Требования ко всему проекту из спецификации: минимальные версии,
ограничения зависимостей, правила имён и текстов, требования платформы.
По одной строке; точные значения копируй дословно. Этот раздел неявно
входит в требования каждой задачи.]

## Особое внимание при проверке

[Пять наиболее вероятных классов входных данных или сбоев, которые
следуют из спецификации, но не проверяются тестами задач, и могут
затронуть пользователя. По строке на каждый случай: данные или условие
и ожидаемое разумным человеком поведение; наиболее вероятное первым.
Спецификация описывает, что программа должна делать, но не всё, с чем
она столкнётся. Молчание о входных данных не разрешает сбой программы.
Один раз составь список по спецификации. Затем добавь для каждого
пункта тест в соответствующую задачу, в принятом для неё стиле.]

---
```

## Структура задачи

````markdown
### Задача N: [Название компонента]

**Файлы:**
- Создать: `exact/path/to/file.py`
- Изменить: `exact/path/to/existing.py:123-145`
- Тест: `tests/exact/path/to/test.py`

**Интерфейсы:**
- Использует: [что задача берёт из предыдущих — точные сигнатуры]
- Предоставляет: [на что опираются следующие задачи — точные имена
  функций, типы параметров и результатов. Исполнитель видит только свою
  задачу; этот блок сообщает ему имена и типы соседних задач.]

- [ ] **Шаг 1: написать падающий тест**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Шаг 2: запустить тест и убедиться, что он падает**

Команда: `pytest tests/path/test.py::test_name -v`
Ожидается: FAIL с сообщением «function not defined»

- [ ] **Шаг 3: реализовать `function(input: InputType) -> ResultType` в `exact/path/to/file.py`**

Одна строка о подходе, если сигнатура и тест оставляют выбор — например,
вызов библиотеки или структуру данных; блок кода только для алгоритма,
который ими не определяется.

- [ ] **Шаг 4: запустить тест и убедиться, что он проходит**

Команда: `pytest tests/path/test.py::test_name -v`
Ожидается: PASS

- [ ] **Шаг 5: создать коммит**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## Содержание шага

Шаг готов, когда исполнитель может написать по нему ровно один разумный вариант. Требование — однозначность, а не полный текст кода. Для каждого типа шага указывай только то, что делает его однозначным:

- **Шаг с тестом:** название теста и его проверки в коде с точными значениями из спецификации.
- **Шаг с кодом:** точную сигнатуру — имя, параметры и возвращаемый тип, файл и конкретные значения из спецификации. Тело пишет исполнитель. Приводи тело только для алгоритма, не определяемого сигнатурой и тестами, или точного текста, зафиксированного спецификацией.
- **Шаг проверки:** команду запуска и вывод, означающий успех.
- **Ссылка на другую задачу:** её блок интерфейсов указывает, что использовать; не повторяй её код.

План — это набор решений, которые исполнитель не может принять самостоятельно. Если план длиннее описываемого кода, он уже превратился в запись программы. Противоположная ошибка — строки без решений: «уточнить позже», «обработать крайние случаи», «добавить нужную проверку», «написать тесты для вышеуказанного», тип или функция, которые ни одна задача не определяет. Самопроверка выявляет обе ошибки.

## Самопроверка

После составления полного плана свежим взглядом сверь его со спецификацией. Этот список выполняешь самостоятельно, без передачи субагенту.

1. **Покрытие спецификации.** Просмотри каждый раздел и требование. Можно ли указать реализующую их задачу? Перечисли пробелы.
2. **Проверка шагов.** Каждый шаг позволяет написать ровно один разумный вариант и не содержит большего. Строка без решения — пробел; тело функции, определённое сигнатурой и тестами, — лишняя запись кода. Исправь оба случая.
3. **Согласованность типов.** Совпадают ли типы, сигнатуры методов и свойства в последующих задачах с определениями в предыдущих? `clearLayers()` в задаче 3 и `clearFullLayers()` в задаче 7 — ошибка.
4. **Особое внимание при проверке.** Для каждого класса данных или сбоя, подразумеваемого спецификацией, есть ли задача с соответствующим тестом? Пять наиболее опасных непокрытых случаев запиши в раздел проверки и добавь тест к задаче-владельцу. Пустой раздел означает, что ты проверил и ничего не нашёл, а не пропустил проверку.
5. **Соразмерность.** Сравни длину плана и спецификации. План в несколько раз длиннее спецификации — запись программы, а не план. Если кодовые блоки занимают большую часть документа, замени тела сигнатурами, именами тестов и проверками, сохранив однозначность каждого шага.

Найденное исправь прямо в плане и продолжай; повторная проверка не требуется. Для требования без задачи добавь задачу.

## Передача к исполнению

После сохранения и самопроверки предоставь пользователю ссылку на план. Если он уже прямо указал способ выполнения, сохрани этот выбор. Если решение или разрешение уже получено, действуй в его рамках. В остальных случаях исходный процесс предлагает попросить проверить план и выбрать способ до реализации.

**Если способ выполнения не указан:** при уже данном поручении самостоятельно выбери допустимый способ по сложности задачи и ограничениям среды. Используй субагентов только при разрешённом делегировании. Обращайся к пользователю за выбором, только если он действительно необходим для продолжения. Ниже — необязательный пример вопроса, а не требование остановить уже разрешённую работу:

> План готов и сохранён в `docs/superpowers/plans/<filename>.md`. Проверь его. Какой подход к выполнению предпочитаешь?
>
> - **Субагенты:** новая задача и новый проверяющий для каждого этапа, затем проверка всей ветки. Тщательно, но требует отдельного контекста для каждого.
> - **В текущей сессии:** я выполняю все задачи в этой среде, затем отдельный проверяющий оценивает всю ветку. Быстрее и дешевле; независимая проверка происходит в конце.
>
> Для этого плана рекомендую <один из способов>, потому что <одно предложение о зависимостях задач, их количестве и цене ошибки>. План отражает желаемое? Какой подход выбрать?

**Если способ выполнения уже указан, но план требует отдельного согласования:**

> План готов и сохранён в `docs/superpowers/plans/<filename>.md`. Проверь: он отражает желаемое?

**Если выбраны субагенты:**
- **ОБЯЗАТЕЛЬНЫЙ НАВЫК:** `superpowers:subagent-driven-development`.

**Если выбрано выполнение в текущей сессии:**
- **ОБЯЗАТЕЛЬНЫЙ НАВЫК:** `superpowers:executing-plans`.
