# Выполнение плана: задачи и итоговая проверка

Правила СУИИР и прямые указания пользователя имеют приоритет. Продолжай уже разрешённую работу без повторного согласования; не удаляй пользовательские данные без необходимого разрешения.

## Цикл задачи

Весь вывод и результаты инструментов остаются в контексте сессии. Перенаправляй длинный вывод тестов в файл рабочей области и читай конец; для задачи читай её краткое задание, а не весь план.

### 1. Возьми задачу

- Запусти `scripts/task-start PLAN_FILE N` этого навыка по абсолютному пути из рабочего дерева. Одним вызовом команда выдаёт путь к заданию и BASE — коммит, от которого отсчитываются изменения задачи. Читай краткое задание каждой задачи, даже если помнишь его после подготовки: память хранит пересказ, а файл содержит точные значения, сигнатуры и тесты.
- Пометь задачу в списке как `in_progress`.

Каждый вызов инструмента повторно использует весь контекст. Совмещай учётные действия с работой: например, дописывай журнал в том же вызове, что и коммит, а не отдельно.

### 2. Выполни шаги

Для применимого TDD следуй циклу RED–GREEN из `superpowers:test-driven-development`. Выбирай проверки по СУИИР и задаче: небольшие обратимые изменения не требуют нового теста только ради процесса. Если проверяешь сценарий через тест до реализации, убедись, что он действительно выявляет проблему.

У каждого шага с командой есть строка `Expected:`. Выполни команду, прочитай вывод и сравни. Возможны три результата:

- **Совпадает.** Переходи к следующему шагу.
- **Код неверен.** Примени `superpowers:systematic-debugging`. Найди причину; не маскируй симптом, чтобы получить ожидаемый вывод.
- **План неверен:** шаг противоречит спецификации, интерфейс предыдущей задачи не совпадает с используемым или команда не может работать. Выбери минимальное исправление согласно спецификации и СУИИР, запиши существенное решение и продолжай. При стоп-условиях СУИИР останови зависимую работу и уточни решение у владельца. Решение хранится в журнале, чтобы позднейшие задачи с тем же интерфейсом могли его прочитать.

Создавай коммиты в соответствии с шагами плана. Задача может включать несколько коммитов; диапазон проверки отсчитывается от BASE, а не обязательно от `HEAD~1`.

### 3. Условия завершения

Прежде чем добавить строку о завершении задачи, подтверди в этой сессии каждый пункт доказательствами, а не по виду diff:

- Все тесты, названные в кратком задании, существуют и выполнены для этой задачи; их вывод прочитан.
- Финальный прогон тестов задачи успешен: его выполняет `task-done`, записывая команду и результат в журнал.
- Каждая строка `Expected:` сопоставлена с фактическим выводом.
- Каждое отклонение от задания имеет строку `Ruling:` в журнале.

**ОБЯЗАТЕЛЬНЫЙ НАВЫК:** заявление о завершении регулирует `superpowers:verification-before-completion`. Если чего-то не хватает, задача не завершена: выполни недостающее.

### 4. Заверши задачу

Запусти `scripts/task-done PLAN_FILE N BASE -- <test command>` этого навыка по абсолютному пути из рабочего дерева, передав команду тестирования всей задачи из задания. Скрипт выполнит тесты, сохранит полный вывод в рабочей области, покажет конец и только при успехе добавит строку:

`Task <N>: complete (commits <base7>..<head7>, tests: <command> → <result>)`

Неудачный запуск ничего не записывает: задача остаётся незавершённой. После записи пометь её завершённой и возьми следующую.

## Итоговая проверка

Запусти `../subagent-driven-development/scripts/review-package PLAN_FILE MERGE_BASE HEAD` по абсолютному пути из рабочего дерева. MERGE_BASE — коммит, от которого началась ветка, например результат `git merge-base main HEAD`. Проверяй материалы в указанном скриптом файле.

**Если доступен инструмент субагентов и его использование разрешено:** привлеки проверяющего на наиболее способной доступной модели: проверка всей ветки требует суждения. Используй шаблон [code-reviewer.md](../requesting-code-review/code-reviewer.md) из `superpowers:requesting-code-review`. Передай путь к пакету, плану и спецификации; дословно передай раздел Review Focus плана, если он есть, чтобы проверить перечисленные классы данных и возможные сбои; укажи на строки `Ruling:` в журнале. Исходный навык предлагает явно указать модель, поскольку без этого наследуется модель текущей сессии. Это единственная проверка со свежим контекстом; не заменяй её собственным чтением diff, когда такой проверяющий действительно доступен и разрешён.

**Если инструмента субагентов нет или его использование не разрешено:** прочитай code-reviewer.md и отдельно проверь пакет после последней строки задачи в журнале. Запиши `Final review: self-review (no subagent tool)` либо укажи фактическую причину отсутствия независимого проверяющего. Сообщи это в итоговом ответе: самопроверка автора слабее независимой, и пользователь решает, достаточно ли её для слияния.

До исправления отсортируй замечания. Уровни критичности проверяющего — рекомендации; решение принимаешь ты. Обработай также список «Declined to judge»: каждую отложенную оценку преврати в решение и запиши как `Final: Ruling: <неоценённое поведение> — <что получит разумный пользователь и почему это допустимо либо теперь считается проблемой> — <цена ошибки>`. Сначала переоценивай по последствиям: спецификация описывает видение, поэтому важен эффект для пользователя, а не факт упоминания конкретного ввода. Если замечание назвали незначительным только из-за молчания спецификации, оценена спецификация, а не последствия.

- **Critical и Important** исправляются.
- **Minor** запиши в журнал как `Final: minor (deferred): <краткое описание>` и включи в итоговый ответ в раздел «Отложенные незначительные замечания». Они не входят в проход исправлений и не становятся решениями Ruling: решение разрешает противоречие, а не фиксирует отказ от косметического улучшения.

Исправь критические и важные замечания. Выбирай воспроизводящий тест или другую проверку по СУИИР и характеру задачи; при применении TDD проверь, что тест выявлял проблему до исправления. Выполни применимые проверки и зафиксируй фактические результаты. Не заявляй об успешной проверке, если она не выполнялась или не подтверждает нужное поведение. Не публикуй релиз при непроходящих обязательных проверках.

Если решаешь не исправлять замечание, запиши решение как `Final: Ruling: <замечание> — <почему код остаётся> — <цена ошибки>` и включи его в список для пользователя. Второго прохода исправлений исходный процесс не предусматривает.

## Завершение

До удаления чего-либо собери все строки журнала с `Ruling:` в раздел итогового ответа «Мои решения» в порядке принятия, включая цену ошибки. Все строки `minor (deferred)` включи в раздел «Отложенные незначительные замечания». Оба списка должны быть полными: через них пользователь узнаёт о принятых от его имени решениях и замечаниях, которые не исправили.

Когда итоговая проверка завершена и исправления закоммичены, исходный навык предлагает удалить рабочую область этого плана: дальнейшая история хранится в git. Соседние каталоги принадлежат другим планам и не затрагиваются. Соблюдай приоритет правил пользователя и защиту данных перед удалением.

Используй `superpowers:finishing-a-development-branch`.

## Типичные оправдания

| Оправдание | Реальность |
|---|---|
| «Я помню задачу N» | Ты помнишь пересказ. Точные значения находятся в кратком задании; прочитай его. |
| «Код плана верный, не буду смотреть падение теста» | Если не видел падение, тест не доказал, что обнаруживает проблему. Запусти его. |
| «Выполню весь набор тестов в конце вместо каждого шага» | Промежуточные запуски показывают, какой шаг сломал поведение. Финальный запуск задачи обязателен, но не заменяет их. |
| «План неверен, просто поступлю правильно» | Поступи правильно и запиши решение. Незарегистрированное отклонение — скрытое решение. |
| «Запишу журнал после нескольких задач» | Сжатие контекста может наступить в любой момент. Записывай каждую задачу вместе с коммитом. |
| «Спрошу перед следующей задачей» | Пользователь выбрал самостоятельное выполнение. Не расходуй его время на повторные вопросы; учитывай реальные основания остановки. |
| «Я внимательно прочитал свой diff, проверяющий не нужен» | У автора те же слепые зоны. Независимый проверяющий даёт свежий взгляд. |
| «Изменение простое, тесты должны пройти» | «Должны» — не доказательство. Нужны команда и её вывод. |
| «Субагенты дорогие, пропущу финальную проверку» | Самостоятельное выполнение уже исключило проверки каждой задачи. Проверка всей ветки — минимальная мера. |
| «Проверяющий сказал Minor, значит Minor» | Оцени последствия для пользователя, затем определи уровень и действие. |
| «Исправление очевидно, падающий тест не нужен» | Тест подтверждает реальность проблемы и её устранение; иначе есть только diff и предположение. |
| «Заодно исправлю мелочи» | Каждая мелочь требует теста, правки и полного прогона. Зафиксируй её; пользователь решит, нужна ли она. |
