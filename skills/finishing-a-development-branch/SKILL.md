# Завершение ветки разработки

## Приоритет правил проекта

В проектах Валерия СУИИР и его прямые указания имеют приоритет. Если решение об интеграции уже принято пользователем в текущем разговоре, не запрашивай его повторно. Требования СУИИР к проверкам, релизу и необратимым действиям обязательны.

## Обзор

**Главный принцип:** проверь тесты → определи окружение → представь варианты → выполни выбор → убери рабочую область.

**Объяви в начале:** «Использую навык finishing-a-development-branch, чтобы завершить работу».

## Шаг 1: проверь тесты

Запусти полный набор тестов проекта (`npm test` / `cargo test` / `pytest` / `go test ./...`).

**Если тесты не проходят**, сообщи о сбоях и остановись: варианты интеграции показываются после успешной проверки.

```text
Тесты не проходят (<N> ошибок). До завершения необходимо исправить:

[Показать ошибки]
```

**Если тесты проходят:** переходи к шагу 2.

## Шаг 2: определи окружение

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# Сохрани путь сейчас, пока находишься внутри рабочей области:
# шаг 5 меняет каталог до очистки на шаге 6
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

Это определяет список вариантов и способ очистки:

| Состояние | Варианты | Очистка |
|---|---|---|
| `GIT_DIR == GIT_COMMON`: обычный репозиторий | Стандартные три | Worktree для очистки нет |
| `GIT_DIR != GIT_COMMON`, именованная ветка | Стандартные три | По происхождению рабочей области, шаг 6 |
| `GIT_DIR != GIT_COMMON`, отсоединённый HEAD | Два варианта без слияния | Управляется извне — оставь на месте |

## Шаг 3: определи базовую ветку

Базовая ветка — та, от которой ответвилась текущая работа. Обычно она указана в плане, разговоре или upstream ветки. Если она неизвестна, спроси: «Эта ветка ответвилась от <наиболее вероятная ветка> — верно?» До слияния подтверди выбор: исправлять слияние в неверную ветку затратно.

## Шаг 4: представь варианты

Если пользователь уже выбрал способ интеграции, используй его выбор. Иначе для обычного репозитория и worktree с именованной веткой покажи ровно три варианта:

```text
Реализация завершена. Что сделать дальше?

1. Слить изменения в <base-branch> локально
2. Отправить ветку и создать Pull Request
3. Оставить ветку как есть (я займусь ею позже)

Какой вариант выбрать?
```

Для отсоединённого HEAD покажи ровно два варианта:

```text
Реализация завершена. HEAD отсоединён, рабочая область управляется извне.

1. Отправить новую ветку и создать Pull Request
2. Оставить как есть (я займусь этим позже)

Какой вариант выбрать?
```

Показывай полный краткий список вариантов. Отбрасывать работу можно только по явному запросу пользователя, как описано ниже. Если решение ещё не принято, дождись ответа.

## Шаг 5: выполни выбранное

### Вариант 1: локальное слияние

```bash
# Перейди в корень основного репозитория
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# Сначала слей ветку и убедись в успехе до удаления чего-либо
git checkout <base-branch>
git pull
git merge <feature-branch>

# Проверь тесты после слияния
<test command>
```

Если после слияния тесты не проходят, остановись, сохрани worktree и ветку и исследуй проблему: слияние локальное и ещё не отправлено.

Когда тесты успешно пройдут, очисти worktree по шагу 6, затем удали ветку:

```bash
git branch -d <feature-branch>
```

### Вариант 2: отправка и создание PR

```bash
git push -u origin <feature-branch>
# Если HEAD отсоединён, назови новую ветку на сервере:
# git push origin HEAD:refs/heads/<new-branch>
```

Создай pull/merge request в `<base-branch>` средствами хостинга: CLI, если он доступен, или по ссылке, которую обычно показывает сервер после push. Соблюдай шаблон PR и соглашения репозитория, если они есть. Передай пользователю ссылку.

Сохрани worktree: в нём можно исправлять замечания к PR.

### Вариант 3: оставить как есть

Сообщи: «Ветка <name> сохранена. Рабочая область остаётся по пути <path>».

### Если пользователь просит отбросить работу

Этот путь возможен только по явной просьбе выбросить работу. Сначала запроси подтверждение:

```text
Будут безвозвратно удалены:
- Ветка <name>
- Все коммиты: <commit-list>
- Рабочая область <path>

Для подтверждения введи 'discard'.
```

Дождись именно этого подтверждения. После него:

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

Затем очисти worktree по шагу 6 и принудительно удали ветку:

```bash
git branch -D <feature-branch>
```

## Шаг 6: очисти рабочую область

**Выполняется для варианта 1 и подтверждённого удаления.** При вариантах 2 и 3 worktree всегда сохраняется. В обоих случаях, требующих очистки, перед этим выполняется переход в корень основного репозитория: удалять worktree нужно извне. Используй значения `GIT_DIR`, `GIT_COMMON` и `WORKTREE_PATH`, полученные на шаге 2 до смены каталога.

**Если `GIT_DIR == GIT_COMMON`:** обычный репозиторий, worktree для очистки нет. Готово.

**Если `WORKTREE_PATH` находится внутри `.worktrees/` или `worktrees/`:** исходный процесс считает, что worktree создан Superpowers и очистка относится к нему:

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # Очистить устаревшие регистрации
```

**Если в удалении отказано** из-за изменённых или неотслеживаемых файлов, в worktree есть материалы, которых может не быть больше нигде: планы, заметки или временные файлы без коммита. Никогда не применяй `--force` по своей инициативе. Покажи пользователю содержимое и спроси:

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```text
Удаление рабочей области отклонено: эти файлы не были закоммичены:

<file list>

1. Закоммитить их в <branch> перед очисткой
2. Переместить в корень основного репозитория
3. Удалить без возможности восстановления

Что выбрать?
```

Выполни выбранное и затем удали worktree.

**В остальных случаях:** рабочая область принадлежит среде хоста — оставь её на месте. Если платформа предоставляет инструмент выхода из рабочей области, используй его.

## Краткая справка

| Вариант | Слияние | Push | Сохранить worktree | Удалить ветку |
|---|---|---|---|---|
| 1. Локальное слияние | да | — | — | да |
| 2. Создать PR | — | да | да | — |
| 3. Оставить как есть | — | — | да | — |
| Отбросить, только по явному запросу | — | — | — | да, принудительно |

## Типичные оправдания

| Оправдание | Реальность |
|---|---|
| «Тесты проходили раньше в этой сессии» | Запусти набор на состоянии, которое собираешься объединить. Успешный запуск доказывает только состояние, на котором он выполнялся. |
| «Очевидно, пользователь хочет слияния» | Способ интеграции определяет пользователь. Учитывай уже принятое им решение; если его нет, представь варианты. |
| «Функция закончена, предложу удалить работу» | Список вариантов ограничен. Отбрасывай только по явной просьбе пользователя. |
| «Фраза “да, убери это” — достаточное подтверждение» | Исходный процесс требует точного слова `discard` для удаления. |
| «PR создан, worktree теперь только мешает» | В нём исправляют замечания к PR. Он остаётся до принятия работы. |
| «Другая рабочая область выглядит старой, уберу и её» | Очищай только worktree в `.worktrees/` или `worktrees/`; остальные принадлежат хосту. |
| «Удаление отклонено, `--force` просто завершит очистку» | Отказ означает, что файлы могут быть только в этом worktree. `--force` удалит их безвозвратно. Покажи файлы пользователю. |
| «После слияния тест, наверное, нестабильный» | Сбой после слияния останавливает процесс. Ветка и worktree сохраняются до выяснения причины. |
| «Базовая ветка очевидно main» | Проверь точку ответвления или спроси: исправление ошибочного слияния дорого. |
| «Push отклонён, поможет force-push» | Удалённая ветка могла измениться. Исследуй причину; force-push возможен только по прямому запросу пользователя. |
